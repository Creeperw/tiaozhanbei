# 数据加载性能优化方案

> 诊断日期：2026-08-06　|　适用仓库：`tiaozhanbei`（FastAPI 后端 + React 前端）
> 现象：进入"教学资源"（/resources）等页面需等待数秒，其他界面也有明显卡顿。

---

## 一、实测基线（浏览器真实请求 + TestClient 复现）

| API | 耗时 | 说明 |
|---|---|---|
| `/api/v1/textbooks/pdfs/catalog` | **3~4 秒** | 教学资源页最慢接口，每次请求都慢（稳定复现） |
| `/api/v1/dashboard/home` | 0.8~1.2 秒 | 学习任务聚合接口，串行执行多项重逻辑 |
| `/api/v1/learning-context` | ~0.2 秒 | 每请求重复做行为上下文聚合 |
| `/api/v1/learning-path` | ~0.2 秒 | 每节点页请求都会重复聚合行为上下文 |
| `/api/v1/learning-routes`、`/qualification-targets` | 20~30ms | 正常 |
| `/knowledge/atlas/nodes`、`/knowledge/atlas/status` | 36~50ms | 正常（内存服务） |

**结论**：慢的主因是 2 个端点（catalog 3-4s + dashboard/home 1s），其余接口都在几百毫秒内。所有页面共同卡顿是因为多数页面加载都会触发 `/dashboard/home` 与重复的行为上下文聚合。

---

## 二、根因分析（按影响排序）

### 🔴 根因 1：catalog 端点对每本书做跨文件系统 stat（3~4 秒，主因）

- 位置：`backend/competition_app/services/textbook_pdf.py` `_public_book()` → `path.is_file()`
- 机制：`GET /api/v1/textbooks/pdfs/catalog` 每次请求都会对 **94 本教材**逐个执行 `is_file()` 检查 PDF 是否存在。
- 关键环境事实：PDF 真实目录位于 **Windows NTFS 盘**（`/mnt/d/qq信息/揭榜挂帅/textbook_pdfs`，131 个文件 / 21GB），WSL 跨文件系统 stat 单次 **5~30ms**，94 次累计 **≈3 秒**。
- 无任何缓存：每次进入教学资源页、每次刷新都重新执行。

### 🔴 根因 2：`load_learning_context` 每请求重复全量聚合（200ms~1s+）

- 位置：`backend/competition_app/integrations/backend_handoff.py:405` `load_learning_context()`
- 机制：内部串行执行 `rebuild_system_data()`（**带行锁**全量聚合学习活动并写库）、`build_l3_behavior_window()`、`build_diagnosis_snapshot()`、`build_learning_window_metrics()`、`build_learning_trends()`、`build_learning_statistics()`、`_load_completed_question_attempts()`。
- 被以下端点**每次请求都调用**（无 TTL 缓存）：
  - `/dashboard/home`（前端学习任务）
  - `/learning-context`（多个页面）
  - `/learning-path` 及其 `/nodes` 子页（**每个 stage/节点请求各调一次**）
  - `/planning/readiness`、`/learning-monitoring/snapshot` 等
- 前端 `DashboardPage` 对每个 stage 发起一次 `/learning-path/nodes` 请求 → N 次重复聚合。

### 🟠 根因 3：`/dashboard/home` 串行重逻辑（约 1 秒）

- 位置：`backend/competition_app/api/app.py:3960` `dashboard_home()`
- 机制：`load_learning_context` → `load_learning_activity_summary` → `ensure_current` → `ensure_executable_daily_resources` → `dispatch_pending` → `reconcile_parent_status` → 计划/队列/会话查询 → **`resolve_topic`（知识库映射检索，逐条执行）**，全部串行 `await asyncio.to_thread(...)`。

### 🟡 根因 4：请求边界中间件每请求额外开销

- 位置：`backend/competition_app/api/app.py:540` `authentication_boundary`
- 机制：每个已登录请求都会执行 `authenticate()` + `load_active_exam_scope()`（或 fallback `infer_active_scope()` SQL 查询）+ `bind_exam_workspace()`。单次约 20~200ms，页面加载 5+ 请求时叠加。

### 🟡 根因 5：前端无刷新级缓存，重复拉取

- `DashboardPage.jsx` 已实现 `teachingResourcesPageCache`（localStorage），但：
  - 上传教材的 `useEffect` **每次进入页面仍重新请求** `/textbooks/pdfs/catalog`；
  - 路径加载（每个 stage 的 `/learning-path/nodes`）没有合并请求接口，冷加载需 N+1 次往返。
- 其他页面（学习路径页、个性化页等）也各自重复调用 `/learning-context`、`/dashboard/home`。

## 三、优化方案（按性价比排序，可独立实施）

### P0｜消除 catalog 的跨盘 stat（预期：3~4s → **<50ms**）

**方案 A（推荐，改动最小）**：启动时预计算可用性并缓存。
- 在 `TextbookPdfService.__init__` 中一次性构建 `self._available_ids: set[str]`（对 catalog 全部书执行一次 `is_file`，启动期 3s 一次性成本），`_public_book` 改为 `book_id in self._available_ids`（O(1) 内存判断）。
- 上传/删除教材时增量更新该集合（已有 `delete_uploaded_book`/导入逻辑，挂一个刷新点）。
- 效果：catalog 从 3-4s → 毫秒级。

**方案 B（备选）**：对 `books()` 结果加 TTL 缓存（如 `functools.lru_cache(maxsize=64, ttl=60s)` 或简单 dict + 时间戳）。简单但有 60s 陈旧窗口，上传后需失效。

**方案 C（一劳永逸，基础设施）**：把 PDF 资源目录迁移到 WSL 原生文件系统（如 `/home/wangjl/data/textbook_pdfs`），或在 `/etc/fstab` 为该挂载启用 `metadata` 选项（drvfs 默认已启用，但中文长路径+大目录仍有损耗）。迁移后单次 stat <0.1ms。

> 建议 A + C 组合：A 立竿见影，C 作为后续整理项。

### P1｜`load_learning_context` 加 TTL 缓存（预期：每请求 200ms+ → 首次 200ms，后续 **<5ms**）

- 位置：`backend/competition_app/integrations/backend_handoff.py`
- 实现：`load_learning_context` 增加进程内 TTL 缓存（按 `(external_user_id, days)` 键，TTL 30~60s），缓存放 `BackendHandoffRuntime` 实例属性。
- 配套：`rebuild_system_data` 改为"窗口内仅重建一次"（例如 5 分钟粒度）或移到后台任务，避免读路径写库+行锁。
- 效果：`/learning-path/nodes`（每 stage 一次）、`/learning-context`、`/dashboard/home` 全部受益。

### P1｜`/dashboard/home` 并行化 + 重操作下移（预期：1s → **~300ms**）

- 位置：`backend/competition_app/api/app.py:3960`
- 实现：
  1. `load_learning_context`、`load_learning_activity_summary`、`ensure_current`、`ensure_executable_daily_resources`、`dispatch_pending`、`reconcile_parent_status` 用 `asyncio.gather` 并行（现在串行）。
  2. `resolve_topic`（知识库映射检索）从请求路径移除或改异步：前端仅展示 kp 名称时不需要它，可延迟到知识卡详情页。
  3. 只读部分（队列、会话、计划）与写路径（dispatch/reconcile）分离，写路径后置。

### P2｜请求边界中间件缓存 scope（预期：每请求省 20~200ms）

- `infer_active_scope()` 结果按 `learner_id` TTL 缓存 30s（scope 变更频率极低）。
- `load_active_exam_scope` 若启用且慢，同样加缓存。

### P2｜前端优化（体验层）

1. **catalog 前端缓存**：`textbookPdfApi.js` 的 `loadTextbookPdfCatalog` 加内存 + localStorage TTL 缓存（60s），避免重复 4s 请求（后端 P0 落地后此条可降级）。
2. **合并路径接口**：新增 `GET /api/v1/learning-path/overview`（一次返回全部 stage + 教材），替代前端对每个 stage 的 N 次 `/learning-path/nodes` 请求；后端在 P1 缓存下此条优先级降低。
3. **先渲染后刷新**：利用现有 `teachingResourcesPageCache`，进入页面先渲染缓存内容，后台静默刷新（当前 `useEffect` 已是此模式，但 catalog 分支每次仍硬请求，改为命中缓存即跳过）。
4. 骨架屏保持现状即可（耗时主要在接口，不在渲染）。

### P3｜基础设施（可选）

- 检查 `/mnt/d` 挂载选项（`mount | grep drvfs`），必要时为资源目录启用 `metadata`。
- 若多用户并发大，考虑给 catalog 响应加 `Cache-Control: max-age=60`（FastAPI 响应头）。

## 四、预期收益汇总

| 项目 | 现状 | 优化后 |
|---|---|---|
| 教学资源页首屏 | 3~5s+ | **<1s**（catalog 毫秒级 + 其余并行） |
| 学习路径页 | ~1s | ~300ms |
| 任意页面冷加载 | 每次全量聚合 | 首次聚合 + 60s 缓存 |
| catalog 接口 | 3~4s | <50ms |

## 五、实施顺序建议

1. **P0 catalog 预计算缓存**（1 个文件，改动 <30 行，收益最大）
2. **P1 load_learning_context TTL 缓存**（1 个文件）
3. **P1 dashboard/home 并行化**（1 个文件，注意 to_thread 语义）
4. **P2 中间件 scope 缓存**（1 个文件）
5. **P2 前端 catalog 缓存 + 路径合并接口**（2~3 个文件）
6. 回归测试：后端 pytest（agents+api+llm+runtime 全量）+ 前端 vitest 全量 + 浏览器实测对比。

> 每步都可独立提交、独立验证，风险可控。P0+P1 落地后即可解决用户感知的"转好一会儿"问题。
