# 知识点覆盖率评测数据构建方案（修订版 v3.1）

> 原稿：`测试方案分支/知识点覆盖率评测数据构建方案.md`
> 原稿已很好的部分（保留）：检索/回答分开评分、required_units 拆分、证据闭合（答对≠有证据）、
> 人工审核流程、不让系统看到黄金标签
> 修订：① 样本口径与 90% 目标的冲突 ② 样本量 ③ 判定落地 ④ 检索口径对齐

---

## 1. 指标定义（对齐赛题 ≥90%）

```
核心知识点覆盖率 = 判定为"已覆盖"的知识点数 / 核心知识点总数   （目标 ≥90%）
```

**"核心知识点"定义（关键修订）**：以**有教材或视频证据支撑**的知识点为"核心"。
资源不足/证据缺失的知识点**不进覆盖率分母**，单独报告"证据充足率"。

理由：原稿 20 个知识点里放 5 个"资源不足"类，覆盖率天花板直接 <75%，必挂。
资源不足是数据问题，不是系统问题，混在一起会掩盖真实检索/回答能力，评委也会质疑。

## 2. 两个子指标（沿用原稿，保留）

| 指标 | 计算 | 说明 |
|---|---|---|
| RAG 检索覆盖率 KPRecall@5/@10 | Top-K 命中 gold_kp_ids 的题数 / 题数 | 多知识点题按集合比例 |
| Expert 回答覆盖率 AnswerCoverage | covered_correct 必答小点数 / 必答小点总数 | covered_correct/covered_incorrect/not_covered 三态 |

附加：证据闭合率 = 回答正确且引用证据的必答小点 / covered_correct 总数（答对≠有证据）。

## 3. 样本量（修订：20 → 100）

- 首轮直接 **100 个知识点 × 2 题 = 200 题**（20 个知识点统计上撑不起 90% 的判断：1 个点错就 5%）
- 构成：双来源 30 / 仅教材 30 / 仅视频 20 / 资源不足 20（不计入分母，单独报告）
- 200 题 × 全链路 ~2.5min ÷ workers 3 ≈ 3 小时，可行

## 4. 判定落地（新增：covered_correct 怎么判）

每道题每个 `required_unit` 独立判定，双通道：
- **通道A（语义匹配）**：embedding 余弦（SiliconFlow Qwen3-Embedding-4B）
  required_unit.content vs 回答对应段落，≥0.75 → covered；<0.50 → not_covered
- **通道B（LLM Judge，DeepSeek）**：给 required_unit + 回答，判 covered_correct/covered_incorrect/not_covered
- A/B 一致 → 采纳；冲突 → 人工复核；抽检 10%

## 5. 检索口径对齐（新增）

- 系统检索返回结构：`evidence_pack`（evidence_items，含 source_id/evidence_id）
- gold 标签必须与系统返回格式一致：先核验 `final_knowledge_points.json` 的 kp_id
  与检索返回的 kp_id 是否同一体系（原稿的 `方剂学_clean:00120` 格式需实际比对一次）
- KPRecall 的 Top-K 与系统实际返回数量对齐（evidence_items 数量不定，脚本里动态取）

## 6. 数据准备（半自动化，减人工）

- required_units 从教材切片自动抽取候选（组成/功效/主治/用法等句段），人工审核确认
- gold_chunk_uids 用切片标题/章节名匹配，人工复核
- 100 知识点 × 2 题 ≈ 600 必答小点，两人分头标，交叉检查

## 7. 执行

```powershell
# 脚本位置：evaluation_delivery/（codex3.py 骨架，按本方案参数化）
python codex3.py --blueprint 100知识点_黄金集.jsonl --judge deepseek --embed siliconflow
```

## 8. 报告

- 核心知识点覆盖率（含 95% CI）+ 分层（按来源/科目）+ 检索覆盖率 + 回答覆盖率 + 证据闭合率
- 失败模式归类：检索失败 / 检索成功但回答不全 / 回答对但无证据（沿用原稿，这是答辩加分点）
- 每个失败案例带 execution_id + snapshot 路径
