## 一、报告摘要

当前系统已经具备题目难度字段的存储、导入、校验和兼容处理能力，但尚未形成完整可用的题目难度功能体系。

系统当前的核心原则是：

> 在正式题库缺少可信、统一的难度元数据时，不自动制造默认难度，不向学习者展示未经验证的“易、中、难”或 `D1-D5` 评级，也不把难度作为训练或组卷的硬过滤条件。

因此，当前系统可以被概括为：

- **已实现**：难度字段预留、数据导入、格式校验、空值治理、难度来源保留、可选难度适配评分。
- **未启用**：前端难度展示、难度选择器、练习按难度筛选、组卷按难度硬约束、自动动态升降难度。
- **当前替代机制**：依据学习者基础、知识点掌握度、正确率、复习状态、题型、题目质量和认知目标组织训练。

## 二、系统现有的难度相关入口

### 2.1 学习者基础画像

前端注册调查页面 `frontend/llm/src/components/OnboardingSurveyPanel.jsx` 会采集学习者的当前基础，例如：

- 零基础；
- 了解基础术语；
- 学过核心课程；
- 具备案例训练基础。

页面文案说明，系统会据此调整讲解深度和训练难度。

但这里的“训练难度”目前主要表示学习内容的起点、讲解深度、任务安排和资源形式，并不是对某道题标记一个正式难度等级，也不是一个可直接用于题目筛选的 `D1-D5` 偏好字段。

### 2.2 训练题目接口

训练题目主要通过以下接口获取：

```text
GET /api/v1/workshop/practice/next
```

当前支持的主要筛选维度包括：

- 知识点 `kp_id`；
- 训练范围 `scope`；
- 训练模式 `mode`；
- 客观题 / 案例题类型；
- 题目状态；
- 已做题记录；
- 题目质量和候选排序。

当前接口没有：

- `difficulty` 查询参数；
- 难度范围筛选；
- 难度排序；
- 难度展示字段；
- “简单 / 中等 / 困难”训练模式。

核心实现位置：

```text
backend/platform_backend/APP/backend/routers/training_routes.py
```

### 2.3 试卷和组卷

当前组卷链路包括：

1. 生成试卷蓝图；
2. 检索题目候选；
3. 形成候选池；
4. 按题型、知识范围和选题规则组卷；
5. 进行审核；
6. 生成试卷和答案解析。

当前前端没有难度下拉框，后端蓝图也没有启用正式的难度偏好字段。组卷时不会将“易 / 中 / 难”或 `D1-D5` 作为题目检索的硬条件。

相关文件：

```text
backend/competition_app/contracts/paper.py
backend/competition_app/agents/paper_blueprint.py
backend/competition_app/prompt_skills/expert_agent/paper_blueprint.md
frontend/llm/src/components/PaperGenerationPanel.jsx
```

### 2.4 个性化推荐和复习资源

个性化资源链路会参考：

- 学习者掌握度；
- 答题正确率；
- 知识点薄弱程度；
- 复习到期状态；
- 题目类型；
- 资源质量；
- 学习目标。

在题目难度元数据完整时，系统还可以计算 `difficulty_fit`，用于评价资源难度是否适合学习者。但是这不是用户可以直接操作的“难度选择功能”。

## 三、题目难度数据结构

### 3.1 题库题目字段

交接业务数据库中的 `QuestionBankItem` 已预留：

```text
difficulty: 可为空
difficulty_source: 可为空
```

含义如下：

- `difficulty`：题目的标准化难度，设计上支持 1 到 5；
- `difficulty_source`：难度来源，例如人工标注、外部题库或审核结果。

实现位置：

```text
backend/platform_backend/APP/backend/database.py
```

### 3.2 题目版本字段

`QuestionVersionRecord` 中包含：

```text
standard_difficulty: 可为空
difficulty_source: 可为空
```

它用于保存题目版本对应的难度快照，避免题目更新后影响历史数据的追溯性。

### 3.3 试卷题目快照字段

`PaperItemRecord` 中包含：

```text
standard_difficulty: 可为空
```

未来如果题目难度正式启用，组卷时可以将当时的难度写入试卷快照，保证历史试卷的题目元数据稳定。

### 3.4 主后端题目载荷

主后端的 `_formal_question_payload()` 会读取题目的：

```text
difficulty
难度
```

并按照以下规则处理：

- 接受数值形式的 1 到 5；
- 兼容 `D1` 到 `D5`；
- 拒绝超出范围的数值；
- 拒绝非法字符串；
- 缺失、为空或非法时转换为 `None`。

实现位置：

```text
backend/competition_app/api/app.py
```

### 3.5 正式内容导入

正式内容导入服务中的 `_optional_difficulty()` 支持将以下数据转换为统一数值：

```text
1、2、3、4、5
D1、D2、D3、D4、D5
```

非法或空值不会被强行转换，而是保留为空。

实现位置：

```text
backend/platform_backend/APP/backend/formal_content_import_service.py
```

## 五、训练链路中的难度使用情况

### 5.1 当前实际筛选条件

训练接口当前主要按照以下条件选择题目：

1. 指定知识点；
2. 指定题型；
3. 题目状态有效；
4. 排除近期已领取或已完成题目；
5. 参考历史作答；
6. 参考题目质量；
7. 按题目 ID 进行稳定排序。

难度不在上述硬筛选条件中。

### 5.2 当前没有的训练功能

系统当前不支持：

- 只做简单题；
- 只做中等题；
- 只做困难题；
- 从简单题逐步升级到困难题；
- 根据连续答对自动升级；
- 根据连续答错自动降级；
- 按知识点分别设置难度；
- 按题型分别设置难度。

### 5.3 当前替代方案

现阶段，系统主要通过以下机制实现个性化：

- 低掌握度知识点优先复习；
- 依据正确率识别薄弱点；
- 依据复习周期安排复习任务；
- 依据题型需求选择客观题或案例题；
- 依据题目质量排序；
- 依据用户基础调整讲解起点；
- 依据认知目标组织识记、理解、辨析和迁移任务。

这些机制可以调节训练体验，但不应表述为已实现正式题目难度控制。

## 六、组卷链路中的难度使用情况

### 6.1 当前组卷依据

组卷主要依据：

- 用户明确提出的学习范围；
- 知识模块；
- 学习目标；
- 题型偏好；
- 目标题数；
- 分值；
- 候选题数量；
- 选题规则；
- 题目来源和证据质量；
- 全卷去重；
- 答案和解析完整性。

### 6.2 当前不允许的组卷行为

当前不允许：

- 使用旧画像中的 `preferred_difficulty` 直接生成试卷难度；
- 根据缺失数据默认生成 `D2`；
- 将难度作为题目检索的硬过滤条件；
- 把题目复杂程度直接转换为未经验证的难度等级；
- 在正式试卷上呈现没有来源的“易 / 中 / 难”。

### 6.3 认知目标替代简单难度

组卷提示词鼓励使用更可解释的认知动作描述，例如：

- 术语识记；
- 概念理解；
- 知识点辨析；
- 病例迁移；
- 综合应用。

这种方式描述的是“题目要求学习者完成什么认知任务”，而不是简单声称题目属于“中等难度”。

当前它主要是组卷提示和选题规则层面的能力，尚未完全结构化到每道题的数据库字段中。

## 七、`difficulty_fit` 难度适配评分

### 7.1 功能定位

`difficulty_fit` 是多尺度学习推荐中的一个评分分项，用来评估资源难度与学习者当前能力是否匹配。

它不是：

- 用户可操作的难度选择器；
- 题库的标准难度标签；
- 训练接口的筛选条件；
- 试卷生成的硬约束；
- 学习者掌握度。

### 7.2 启用条件

只有以下数据可用时，`difficulty_fit` 才有可能计算：

- 资源或题目有可信难度；
- 学习者有足够的掌握度或答题表现证据；
- 系统可以比较题目难度与学习者能力。

### 7.3 数据缺失时的行为

当题目难度缺失时，系统会返回不可用状态，例如：

```json
{
  "available": false,
  "value": null,
  "unavailable_reason": "difficulty_metadata_missing"
}
```

随后推荐系统会忽略这一项，并重新计算其他可用评分，不会把 `difficulty_fit` 当作 0 分，也不会凭空推断题目难度。

实现位置：

```text
backend/platform_backend/APP/backend/multiscale_learning_service.py
```

## 八、几个容易混淆的概念

| 概念 | 含义 | 是否等于题目难度 |
|---|---|---:|
| `difficulty` | 题目难度元数据，设计上支持 1-5 | 是 |
| `difficulty_source` | 难度来源 | 否，是来源说明 |
| `mastery` | 学习者对知识点的掌握程度 | 否 |
| `accuracy` | 学习者历史答题正确率 | 否 |
| `score` | 某次作答或试卷得分 | 否 |
| `quality_score` | 题目内容质量或候选排序分 | 否 |
| `difficulty_fit` | 题目难度与学习者能力的匹配评分 | 否，是匹配度 |
| `foundation_level` | 学习者自报基础水平 | 否，是画像信息 |
| `target_difficulty` | 历史快照中的旧目标难度字段 | 当前不作为正式功能使用 |
| `preferred_difficulty` | 历史难度偏好字段 | 当前已清理或忽略 |

特别需要注意：

- 学生掌握度低，不代表题目一定困难；
- 学生答错，不代表题目客观难度高；
- 题目质量高，不代表题目难度高；
- `difficulty_fit` 高，只代表题目可能更适合当前学习者；
- 旧数据中的 `D2` 不代表当前系统已经启用默认中等难度。

## 十、后续建设建议

如果后续要正式启用题目难度功能，建议按以下顺序建设。

### 阶段一：建立可信标注

1. 明确难度标准，例如 1-5 级；
2. 明确每一级的判定规则；
3. 区分客观题、简答题和病例题的难度标准；
4. 给每条难度增加来源和版本；
5. 设置人工审核状态；
6. 先对小规模题库进行试标和抽检。

### 阶段二：建立校准闭环

1. 采集答题正确率；
2. 采集答题耗时；
3. 采集不同基础学习者的表现；
4. 统计题目区分度；
5. 识别异常题目；
6. 根据实际数据修正难度。

### 阶段三：开放非强制推荐

在难度数据达到可信度后，可以先开放：

- 难度信息展示；
- “推荐难度”提示；
- 难度适配说明；
- 题目难度分布报告。

此阶段仍建议不要直接做硬过滤，以避免因数据缺失造成无题可做。

### 阶段四：开放训练和组卷控制

最后再考虑开放：

- 按难度练习；
- 难度范围筛选；
- 难度递进训练；
- 组卷难度比例；
- 根据连续答题表现动态调节难度。

所有难度筛选都应保留降级策略：当指定难度题目不足时，系统应提示数据不足或扩大候选范围，而不是直接返回空题目列表。

## 十一、最终结论

当前系统具备的是“题目难度能力的基础设施”，而不是完整的“题目难度产品功能”。

现阶段最准确的产品表述是：

> 平台根据学习者基础、知识点掌握度、正确率、复习状态、题型、题目质量和认知目标组织个性化学习；题目难度字段已完成兼容和预留，但由于正式题库暂缺统一可信的难度元数据，系统目前不按易、中、难或 D1-D5 对题目进行展示、筛选和组卷。

在正式启用难度功能前，首要任务不是增加一个难度下拉框，而是先建立可靠的难度标注、来源、审核和数据校准体系。
